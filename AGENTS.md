# Crypto Style Matrix frontend

## Scope

This repository is the React/TypeScript frontend for Crypto Style Matrix. It is built with Vite and deployed to GitHub Pages under the `/frontend` base path. The application integrates TON Connect, profile contracts, Marketing V3 contracts, and the referral-program backend APIs.

Use this file as the default guidance for changes anywhere in this repository.

## Commands

- `npm run dev`: start the Vite development server.
- `npm run build`: run the TypeScript project build and create the Vite production bundle.
- `npm run lint`: run ESLint across the repository.
- `npm run preview`: serve the production bundle locally.

Run `npm run build` after implementation. Run `npm run lint` when the task changes application code; distinguish pre-existing lint findings from regressions introduced by the change.

## Working rules

- Preserve unrelated user changes. The working tree may already be dirty.
- Use TypeScript types that match API JSON exactly. Perform UI aggregation in separate view models instead of changing transport DTOs.
- Do not edit `dist/`; it is generated by the production build.
- Keep each page and non-trivial component paired with its own CSS file. Reuse shared CSS only when the UI is genuinely shared.
- Use `rg`/`rg --files` to find implementations and references before adding or deleting code.
- Do not retain dead compatibility code unless an active route or component still depends on it.

## Application structure

- `src/App.tsx`: top-level providers and routes.
- `src/pages/`: route-level pages.
- `src/components/`: reusable and feature-specific UI.
- `src/context/`: profile, program, marketing, and structure state.
- `src/services/`: backend clients, contract API clients, metadata loading, and transaction orchestration.
- `src/contracts/`: only wrappers still required by the frontend. Prefer backend contract endpoints over adding client-side wrappers.
- `src/programs.ts`: the source of truth for hardcoded marketing contract addresses.
- `public/series-marketing-*.json`: off-chain program metadata.
- `public/locales/<language>/translation.json`: UI translations.

## Routing and programs

Generic Marketing V3 programs use routes under `/programs/:marketingAddress/*`. The default child page is `inviter`. The marketing address must come from the program route/context and must not be silently replaced by a profile or top-place address.

The legacy `/multi` implementation has been removed. Do not recreate it. Multi now uses the generic program flow. The legacy Neo pages still exist where referenced.

### Actual versus test deployments

All address constants live in `src/programs.ts`:

- Actual production program constants must start with `ACTUAL_`.
- Test deployment constants must start with `TEST_`.
- `TEST_PROGRAM_ADDRESSES` defines the displayed test-program order.
- Never move a test address into `AvailablePrograms` or an actual address into `AvailableTestPrograms`.

`AvailablePrograms` displays actual Multi, Neo, and CryptoCash programs.

`AvailableTestPrograms`:

- is visible only when the connected wallet is in `appConfig.availableTestPrograms.walletAddresses`;
- supports the comma-separated `VITE_AVAILABLE_TEST_PROGRAM_WALLETS` environment variable;
- compares normalized raw TON addresses, not display-formatted strings;
- loads only `TEST_PROGRAM_ADDRESSES`.

## Program metadata

Program cards and program marketing pages use metadata obtained from the Marketing V3 basic-data endpoint and its `metadata_uri`.

- Prefer the URI returned by the contract.
- If that URI is unavailable, `programsService` may fall back to the bundled `series-marketing-{index}.json` file.
- Resolve relative and IPFS image URLs safely.
- Preserve all presentation language keys: `de`, `en`, `es`, `fr`, `hu`, `it`, `kk`, `pl`, `pt`, `ru`, `uk`.
- For presentations, use the selected language, then English, then hide the presentation action if neither exists.
- Do not invent financial totals. Add `incomes` only when a source provides a clear total and period.

## API and contract boundaries

### Profiles

The UI backend is the source of truth for the wallet's saved profile list.

- Check wallet profiles even when the local list is empty; this supports first use on another device.
- The check operation already returns the current profile list. Do not immediately issue a redundant get-profiles request.
- Legacy cookie/local-storage profiles are migrated once: add them to the backend, then remove successfully migrated local entries.
- A profile that does not belong to the connected wallet remains saved in `preview` mode instead of being deleted.
- Preview profiles use the normal UI. Transaction confirmations must clearly warn that the action is for a foreign profile.
- Profile display data in generic program pages/components must come from APIs, not profile contract wrappers.

### Program API

Keep program API response types faithful to their snake_case JSON fields. Examples include `profile_addr`, `place_number`, `structure_number`, `created_at`, and `activated_at`.

- Unix timestamps returned as numbers are seconds; convert with `new Date(value * 1000)`.
- A place is uniquely identified by `profile_addr + place_number`.
- `profile_addr` may be `null` for a system place. Its `place_number` is still meaningful and unique within the relevant scope.
- Paginated lists use stable composite keys, never `place_number` alone when collisions are possible.

### Contract API

Prefer the contracts backend for:

- Marketing V3 basic/full data;
- deterministic or serialized exec-message bodies;
- Jetton transfer bodies;
- Jetton minter data and metadata;
- profile and collection contract reads still required by non-program flows.

Do not reintroduce removed legacy Multi contract endpoints or wrappers.

## Structure page semantics

Structure `0` is special: it represents inviter/referral relationships and is not included in the selectable business-structure list.

For user-facing terminology:

- if the selected structure has `height > 0`, describe it as a matrix;
- if `height === 0`, describe it as a level;
- localize the corresponding term in every supported language;
- tree details use “line”, not “level”.

`max_places_per_profile === 0` means unlimited places.

### Tree nodes

The backend is authoritative for node actions. Do not reproduce lock/buy eligibility rules in the frontend when the node supplies them.

- Use `can_buy` and `buy_command_tag` for buying from an empty node.
- Use `include_position` to decide whether to serialize the selected position.
- Use `can_lock` and `can_unlock` to show lock/unlock actions.
- Use `locked` and `is_lock` only for node state/presentation as defined by the API.
- `buy_top_place` is no longer supported. Do not add fallback logic for it.
- Pass `viewer_profile_addr` as the currently selected profile address when loading a tree.

System places have a null profile address:

- display `SC` (“System Clones”) instead of `-` or a login;
- use the standard system/default image in details;
- allow selection and tree loading with a null `profile_addr` when the API permits it.

For a filled node, details may include rank, matrix place count, descendants, line, active state, creation date, and activation date. Hide matrix-place count when `height === 0`. Rank badges use solid, rank-specific colors without gradients and without excessive rounding.

### Buying places

The general buy-button decision is:

1. Load the selected profile's places count.
2. Load the selected structure configuration.
3. Hide the button when the non-zero maximum has been reached.
4. When the count is zero, use `buy_first_place` if that command is supported.
5. Otherwise use `buy_place` if supported.
6. Otherwise hide the button.

For tree-node purchases, prefer the node's `buy_command_tag` and `include_position` fields.

Price, Jetton sender wallet, and gram fee belong to the selected command, not globally to a structure context.

- TON prices are nanotons and must be formatted with `fromNano`.
- Jetton decimals and symbol come from Jetton minter data/TEP-64 metadata. Never assume six decimals or hardcode `USDT`.
- Check Jetton balance before sending only through an implemented API endpoint; do not fabricate a client-side balance mechanism.
- For Jetton purchases, build the Marketing V3 exec body first, embed it in the Jetton transfer body, and use the connected wallet as the response destination.

After sending a user command, refresh the marketing queue immediately. When a tracked purchase task disappears, compare `getLastPlace` with the previous last place, refresh structures data, select the new place, and clear the pending-purchase notification.

## Referrals and inviter

- Use the spelling `referrals` in code and routes unless matching an external API's intentionally misspelled namespace.
- Program referrals use the marketing address from context.
- Referral pagination defaults to a page size of 20.
- Program inviter data comes from `getInviterData(marketingAddr, profileAddr)`.
- A 404 means no curator is set and the chooser is shown, unless a choose-inviter task is already processing.
- In Russian UI text, use “Куратор”, not “Пригласитель”. Apply the equivalent meaning in other languages.

## Statistics

Program statistics come from `GET /api/program/{marketing_addr}/statistics`.

- Partner counts use `total_profiles` and `active_profiles`, not place-row counts.
- `total_places` and `active_places` describe places and must not be relabeled as unique partners.
- Structure `0` is the referral structure and should be presented according to the current statistics layout requirements.
- Keep direct-referral data distinct from whole-structure partner totals.

## Localization

Every user-visible string added or changed in program pages/components and profile flows must be localized in all supported locales: `de`, `en`, `es`, `fr`, `hu`, `it`, `kk`, `pl`, `pt`, `ru`, `uk`.

Do not rely on an English `defaultValue` as the completed localization. Keep translation keys semantically consistent across locale files.

Important established wording:

- Russian inviter: `Куратор`.
- Russian test-program heading: `Программы на стадии тестирования`.
- Russian business structures: `Матрицы` when matrix-shaped, otherwise `Уровни`.
- Russian tree detail “level”: `Линия`.

## UI behavior

- Program/profile address controls are compact text plus icon buttons, with transparent backgrounds and vertically centered icons.
- Copy actions should provide a short visible success effect and reset when the selected address changes.
- Long profile logins in the top-right selector must truncate with an ellipsis.
- The current profile in the open selector should be visually distinguished.
- Do not show a permanent preview-mode warning block.
- TON Viewer links use `https://tonviewer.com/{address}` and should be icon actions where established.

## Verification checklist

Before finishing a change:

1. Search for stale imports, routes, constants, and translation keys.
2. Validate edited JSON metadata and locale files.
3. Confirm actual/test program addresses remain in the correct collections.
4. Run `npm run lint` for application-code changes.
5. Run `npm run build`.
6. Report any remaining Vite chunk-size warning separately from actual build errors.
